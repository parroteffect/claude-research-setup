# Interactive research — phase 안에서는 자율 연구, 전환은 사용자 선택

사용자가 명시적으로 선택한 과제에 적용하는 선택적 workflow다.
기본 연구의 발명·수학적 분석 기준은 `.claude/research-workflow/guides/research.md`를 따른다.
Monk는 정보 사용 정책, goal은 자율 진행 overlay이며 이 workflow와 독립이다.
새 agent 역할, native Claude Code 설정 key, 별도 실행기나 transition guard를 추가하지 않는다.

## 선택과 적용 범위
- “이 과제는 interactive-research로 진행하자”처럼 사용자가 요청하면 활성화한다.
  설명·설치·guide 열람만으로 활성화하지 않으며 다른 과제에 자동 확장하지 않는다.
- Main은 이미 합의한 질문·제약과 사용자 선택을 바탕으로 현재 phase를 정한다.
  출발점이 명확하면 형식적인 재확인을 요구하지 않는다. 중요한 범위가 모호하면
  전환에 의존하는 작업만 보류하고 현재 범위의 유용한 분석을 계속한다.
- Phase 안에서는 요청한 깊이까지 문제 탐색·유도·반례 점검·대안 비교를 자율적으로 수행한다.
  사용자에게 사소한 사고 단계마다 허락을 구하거나 첫 후보와 계획만 보고 멈추지 않는다.
  고정된 후보 수·반복 횟수·매 응답 양식을 요구하지 않는다. 완성된 증명이나 novelty 확정은
  연구 시작의 선행 조건이 아니다. 사실·관찰·가설·proof gap·미확인 novelty를 구분한다.

## 질문에 맞춰 사용하는 다섯 phase

다음은 조정 가능한 연구 구분이다. 모든 과제를 1부터 시작하거나 다섯 단계를 전부 수행할
필요는 없다. 사용자가 선택했거나 이미 명시적으로 승인한 범위에서 건너뛰기·되돌아가기가
가능하며, 이전 판단·실패·근거를 보존한다. Phase 번호 자체는 구현·실행 권한이 아니다.

| Phase | 중심 질문과 남길 근거 |
| --- | --- |
| 1. 중요한 문제 탐색 | 무엇이 중요하며 해결하면 어떤 기여가 남는가? 문제 후보·제약·중요성의 근거와 추천 질문을 발전시킨다. |
| 2. 원인·headroom 진단 | 문제가 실제로 존재하며 왜 생기는가? 기존 결과·경쟁 설명·가벼운 진단으로 병목과 개선 여지, 미확인 가정을 구분한다. |
| 3. 메커니즘·방법 설계 | 어떤 원리로 원인을 바꿀 수 있는가? 서로 다른 메커니즘, 핵심 유도·실패 조건과 판별 예측을 발전시킨다. |
| 4. 최소 판별 구현·검증 | 제안한 방법이 문제를 해결하는가? 승인된 명세의 구현과 기준 비교로 핵심 효과·경쟁 설명을 구별한다. |
| 5. 확대 검증·논문 주장 | 효과가 어느 조건까지 성립하며 무엇을 주장할 수 있는가? 확대 비교·일반화·한계·선행 대비 차이를 근거와 연결한다. |

Phase 2의 probe는 **문제의 존재·원인·headroom**을, phase 4의 검증은 **방법의 해결 효과**를
묻는다. 같은 작은 계산도 목적과 결론의 범위를 구분한다. 진단 결과를 방법의 효과로,
toy 검증을 실제 규모의 성능·일반화로 확대하지 않는다. Phase 5에서도 monk가 켜져 있으면
관련 방법론 대조는 사용자의 별도 요청까지 미확인으로 남긴다.

Phase 3에서는 구현 전에 핵심 수식·처리 흐름과 기대하는 scientific contribution을 구체화한다.
관련되는 경우 offline training, online compression, decoding 각각의 계산 비용과 저장 bytes를
분리해 설명하고 추정치와 실측치를 구분한다. Standard에서는 가장 가까운 선행 접근과의 차이와
확인 근거를 남긴다. Monk에서는 허용된 자료·독립 유도로 설계를 발전시키고 관련 방법론 대조와
novelty는 UNVERIFIED로 남긴다. 이 설계 근거는 완전한 증명·성능 실측을 선행 조건으로 요구하거나
새로운 비용 측정 실험을 자동 실행하라는 뜻이 아니다.

## 사고·진단과 구현의 경계
- 현재 질문에 필요한 수학적 사고, 메커니즘 sketch, 작은 반례·cheap diagnostic은 기존의
  가벼운 local test 범위 안에서 가능하다. 잠정 해법을 생각했다고 다음 phase로 전환한 것은 아니다.
- 진단을 명목으로 승인되지 않은 방법을 프로젝트에 구현하지 않는다. Main의 임시 일회성
  계산과 engineer의 재사용 코드·테스트 작성 책임은 CLAUDE.md를 따른다.
  프로젝트 코드 변경은 기존 구현 승인·SPEC·single-writer 규칙을 그대로 따른다.
- Phase 4로 진행하라는 명확한 요청에 구현 범위가 포함되어 있으면 그 범위를 실행한다.
  추가 형식적 승인은 요구하지 않되, 미정 핵심 조건이나 범위 밖 변경은 main에 반환한다.
  승인된 구현 내부의 세부 phase마다 사용자 재승인을 요구하지 않는다.
- 모든 phase에서 USER-ONLY를 유지한다. 무거운 학습·평가·준비·확대 검증은 사용자가 실행한다.
  비용 미확인 작업도 실행하지 않는다. 필요한 RUNBOOK과 미검증 항목을 남기며,
  가벼운 검증 PASS·실행 준비·본 실험 완료·가설 지지를 구분한다.

## Phase 경계의 대화와 선택
- 현재 phase의 결과와 추천 방향, 핵심 불확실성·남은 결정, 제안하는 다음 phase와 범위를
  짧게 보고하고 사용자의 선택을 기다린다. 현재 phase에서 얻은 근거를 함께 제시한다.
  전환 선택 전에는 다음 phase의 작업을 시작하지 않는다.
- 문맥상 제안한 전환이 하나로 명확하면 “그걸로 진행해”도 충분한 선택이다.
  이미 명시적으로 승인한 전환을 다시 확인하지 않는다. 칭찬이나 침묵은 전환 동의가 아니다.
  여러 방향 중 무엇을 선택했는지 불명확할 때만 필요한 결정을 확인한다.
- 사용자는 계속 탐색, 다른 방향, phase 건너뛰기·복귀, 일시정지·종료를 선택할 수 있다.
  되돌아가도 과거 근거를 지우지 않는다. 새로운 반례가 있으면 추천을 수정하고 이유를 밝힌다.
- 사용자 선택, 가설 지지, novelty 상태, phase 완료, 전체 목표 완료는 별개다.
  경계에서 기다린다는 것은 전체 연구 성공을 뜻하지 않는다.

## Goal·monk와 함께 사용할 때
- Interactive 선택·해제만으로 goal이나 monk를 켜거나 끄지 않는다. 기존 목표·예산·ledger,
  과거 연구 기록과 사용자의 실행 중 job도 초기화·변경하지 않는다.
- Goal의 자동 진행은 phase 경계를 넘을 동의가 아니다. 현재 phase 안에서만 합의한
  bounded progress를 수행하고, 경계에서는 사용자 선택을 기다린다. 현재 phase 산출물을
  완료해도 더 넓은 ultimate goal의 조건이 남으면 GOAL_MET로 표시하지 않는다.
  기존 ultimate goal을 phase 목표로 조용히 축소하거나 config를 재작성하지 않는다.
- `.claude/research-workflow/guides/goal.md`의 관련 계약·예산·독립 QA/Supervisor·실행 gate를 유지한다.
  순수 연구 phase에는 수치 proxy 선행 조건을 억지로 만들지 않는다. Goal guide의 순수 연구
  계약처럼 판단 기준과 평가 근거를 명시하고, 실제 proxy를 실행할 때 그 gate를 적용한다.
- 경계 대기와 재개에도 기존 elapsed clock·소모·pending·실패 기록을 유지한다.
  Phase 선택은 예산 증액·reset·재예약·job 재시작의 허가가 아니다.
- Monk의 허용 자료·선행연구 대조 시점은 `.claude/research-workflow/guides/monk.md`를 따른다.
  사용자 전환 선택이 가설의 검증이나 문헌상 novelty 확인을 대신하지 않는다.

## 최소한의 상태와 위임
Main은 기존 `research/STATE.md`에 필요할 때만 작은 선택적 항목을 추가한다.
활성 여부·적용 과제와 선택 근거, 현재 phase, 합의한 질문·제약,
상태(`working` / `awaiting-user` / `paused` / `closed`), 선택 방향·근거 링크,
다음 사용자 결정을 짧게 남긴다. 별도 사용자 작성 config나 매번 새 문서는 요구하지 않는다.
기존 STATE는 설치 시 create-only로 보존하며 템플릿으로 덮어쓰지 않는다.

재개할 때 해당 과제의 phase·선택 근거·미결정을 복원한다. Awaiting-user를 자동 전환으로
해석하지 않는다. 해제·종료 뒤에도 근거와 미완료 목표를 보존한다.
Main은 engineer 및 관련 reviewer에게 현재 phase, 허용 작업, 전환 대기 여부와 이 guide를
전달한다. Engineer는 위임한 범위를 자율적으로 완료하고 경계를 넘는 판단은 main에 반환한다.
이 문서는 대화 운영 지침이며 runtime 강제나 연구 품질·창의성 향상을 검증한 결과가 아니다.
